# تطبيق وفر دوام الأصلي — iOS وAndroid

المشروع `mobile/` هو بوابة الموظف المكتوبة بـReact Native وExpo SDK 58. الشاشات وعناصر التحكم والتنقل أصلية، وليست صفحات ويب أو WKWebView أو TWA. واجهة الإدارة على الموقع مستقلة. البيانات مشتركة عبر API السيرفر الحالي وقاعدة PostgreSQL الحالية؛ لا توضع بيانات اتصال قاعدة البيانات داخل التطبيق.

## الموجود في التطبيق

- الدخول بحساب الموظف وتخزين الجلسة في Keychain/Keystore عبر SecureStore؛ البيانات المؤقتة في الذاكرة وتُمسح عند الخروج.
- الحضور والانصراف والفترتان عبر GPS فعلي والتحقق على السيرفر، وحالة العمل والاستراحة وموعد العودة والتأخير.
- الجدول المنشور فقط، وكشف الحضور الشهري والتأخير والغياب، بتقويم ميلادي وتوقيت الرياض.
- طلب إجازة وتغيير شيفت وتبديل وتصحيح بصمة. أذونات إلكترونية مع توقيع بالإصبع ومشاركة رابط اعتماد المدير.
- تعديل الملف الشخصي والصورة والبريد وتأكيد البريد بالرمز.
- تسجيل Passkey أصلي والتحقق من إثبات السيرفر عند البصمة. السياسة الحالية للشركة واعتماد الإدارة للمفتاح يظلان ساريين. إذا كانت الخدمة إلزامية، تُحجب البوابة حتى تسجيل واعتماد المفتاح.
- تسجيل إشعارات Expo الأصلية وتفضيلات الحضور والانصراف وإلغاء الاشتراك. الخادم يكرر التذكير كل 10 دقائق، لأول ساعة فقط، ويوقفه بعد البصمة. الاشتراك ينتهي بعد 30 يومًا؛ زر التجديد يعيد تسجيله.

لا يوجد حفظ بصمات دون اتصال أو تسجيل حضور خلفي غير مؤكّد. الوصول إلى GPS عند طلب البصمة فقط. المشروع ليس مزوّدًا بحسابات أو بيانات موظفين تجريبية.

## التشغيل على الماك

يتطلب Node 22.13 أو أحدث (اختُبر أيضًا على Node 24) وXcode متوافقًا مع SDK 58 وCocoaPods. من مجلد المشروع:

```bash
cd mobile
npx --yes npm@11.9.0 ci
cp .env.example .env.local
npx expo run:ios --configuration Release
```

لأندرويد يلزم Android Studio وJDK 17:

```bash
cd mobile
npx --yes npm@11.9.0 ci
npx expo run:android --variant release
```

الحد الأدنى الحالي iOS 16.4 وAndroid 9 (API 28).

وحدة Passkey تتطلب بناء التطبيق الأصلي؛ Expo Go لا يحتوي عليها. الاسم المعروض **وفر دوام**، والمعرف للمنصتين `com.xshadox.wafrdawam`. إصدار Android يحمل versionCode=4 وiOS buildNumber=3؛ ارفع الرقم إذا سبق نشر رقم أعلى.

## بناء المتاجر

من `mobile/`:

```bash
npx eas-cli@latest login
npx eas-cli@latest init
# ضع معرف المشروع الناتج في EXPO_PUBLIC_EAS_PROJECT_ID قبل البناء
npx eas-cli@latest build --platform all --profile production
```

استخدم حساب الشركة و**نفس مفتاح رفع Google Play السابق** لتحديث التطبيق المنشور. لا تنشئ هوية جديدة أو مفتاحًا بديلًا دون مطابقة إعدادات Play. بناء EAS للإنتاج يطلب بيانات توقيع الشركة؛ لا يمكن إخراج IPA قابل للتوزيع قبل توافر شهادات وحساب Apple المناسبين. مشاريع Xcode وGradle تُولد بـ`npx expo prebuild`، ولا تُعدّل يدويًا في المستودع.

Workflow `Native employee mobile` يفحص TypeScript وESLint والاختبارات ويصدر حزم JavaScript لكل منصة ثم يجمع Android وiOS ويشغّل APK على محاكي Android للتحقق من ظهور شاشة الدخول الأصلية. حزم CI للتحقق من البناء: Android يستخدم مفتاح debug الافتراضي الذي يولده Expo، وiOS غير موقّع. ليست هذه توقيعات رفع المتاجر. حزم المتاجر الموقّعة تُبنى بملف `production` عبر EAS وحسابات الشركة.

## تفعيل Passkey الأصلي

- السيرفر: `APP_URL=https://attendance.xshadox.com` و`WEBAUTHN_ORIGIN=https://attendance.xshadox.com` و`WEBAUTHN_RP_ID=attendance.xshadox.com`.
- iOS: اضبط `APPLE_TEAM_ID` على السيرفر ليقدّم تلقائيًا ملف الارتباط. ويمكن أيضًا نشر `/.well-known/apple-app-site-association` مع `webcredentials.apps` بقيمة `APPLE_TEAM_ID.com.xshadox.wafrdawam` الحقيقية. التطبيق يعلن Associated Domains تلقائيًا؛ يلزم توقيع entitlement بحساب Apple الصحيح.
- Android: اضبط `ANDROID_APP_CERT_SHA256` بقائمة بصمات الشهادات مفصولة بفواصل؛ السيرفر ينشر الارتباط ويشتق origins المسموحة تلقائيًا. عند إدارة الملف خارجيًا أضف العلاقة `delegate_permission/common.get_login_creds` إلى `/.well-known/assetlinks.json` مع المعرف نفسه وبصمة SHA-256 **لشهادة App Signing الفعلية من Play**. عند تثبيت نسخة موقّعة بمفتاح آخر، أضف شهادتها المعتمدة صراحة.
- اختياريًا للشهادات المدارة خارجيًا: `WEBAUTHN_ANDROID_ORIGINS` قائمة مفصولة بفواصل من `android:apk-key-hash:<base64url SHA-256 certificate digest>`، بدون padding. لا تستخدم wildcard، ولا تضف شهادة لا تخص تطبيق الشركة.
- بدون هذه المطابقة، يفشل تسجيل Passkey بأمان ولا يتم تجاوز سياسة الحضور. المفاتيح يمكن أن تتزامن عبر Apple/Google؛ لا تمثل ضمانًا لمنع مشاركة الحساب وحدها.

## إشعارات iOS وAndroid

1. أنشئ مشروع EAS وأضف معرفه الحقيقي إلى `EXPO_PUBLIC_EAS_PROJECT_ID` في إعدادات البناء.
2. جهز APNs من حساب Apple وFCM v1 من Firebase للتطبيق نفسه، وارفع مفتاح الإرسال الخاص عبر `npx eas-cli@latest credentials`. لأندرويد نزّل أيضًا ملف إعداد العميل `google-services.json` المطابق للمعرف `com.xshadox.wafrdawam`، واضبط `GOOGLE_SERVICES_JSON` بمساره محليًا أو كمتغير File في EAS، ثم أعد بناء التطبيق. هذا الملف مختلف عن مفتاح Service Account الخاص؛ المفتاح الخاص يبقى في EAS ولا يضمّن في التطبيق.
3. إذا فعّلت enhanced push security، ضع `EXPO_ACCESS_TOKEN` على السيرفر فقط؛ لا تضعه في متغير `EXPO_PUBLIC_*`.
4. بعد إعداد الاعتمادات فعّل `NATIVE_PUSH_ENABLED=true` على السيرفر. افتراضيًا الإرسال متوقف وتظهر الحالة الحقيقية في التطبيق.
5. من هاتف حقيقي اربط الإشعارات ثم اختبر الحضور والانصراف أثناء إغلاق التطبيق. قبول طلب مزود الإشعارات لا يضمن وصوله؛ عامل السيرفر يتابع receipts ويحذف DeviceNotRegistered.

الإشعارات لا تحتوي أسماء الموظفين أو مواعيدهم أو مواقعهم. الخروج يحذف جلسة الدخول من الجهاز حتى إذا تعذر إلغاء اشتراك الإشعارات على السيرفر. تتم محاولة الإلغاء بمهلة محدودة، وتظهر رسالة توضح التعذر وخيار إيقاف الإشعارات من إعدادات الهاتف. شاشة تعذر تحميل سياسة الباس كي تتيح أيضًا الخروج أو تبديل الحساب.

## نشر السيرفر والانتقال

حدّث السيرفر أولًا لوجود `/api/mobile/*` ودعم Android passkey origins، ثم وزّع التطبيق الجديد. لا تتطلب التغييرات جداول PostgreSQL جديدة، وتبقى سياسات المواقع والحضور والاستراحات والباس كي في السيرفر.

الملفات القديمة في `ios/WafrDawam` و`scripts/generate-android-preview.cjs` تخص الإصدار السابق الذي يعرض الموقع. تبقى كمرجع للتوقيع والهجرة فقط، وليست مصدر بناء التطبيق الجديد. استخدم `mobile/` وWorkflow `Native employee mobile` للإصدارات التالية.

## دخول الموظف والموافقات

التطبيق خاص بدخول الموظف الحالي وحضوره وطلباته وإدارة ملفه. إنشاء الشركة والتسجيل وطلب حساب جديد وإدارة الأقسام والصلاحيات والإعدادات تتم من الويب فقط؛ لا توجد شاشة تسجيل أو دخول إداري في التطبيق.

لإتاحة الموافقات لموظف: من الويب ← المستخدمون والصلاحيات ← تعديل/إضافة المسؤول ← «ربط الموافقات بحساب الموظف في التطبيق»، اختر حساب الموظف وفعل «الموافقة على طلبات الموظفين ورفضها» (`canApproveRequests`) وحدد الأقسام ثم احفظ. الربط صريح ولا يُستنتج من تشابه الاسم أو البريد. الموظف يدخل بحسابه المعتاد وتظهر قائمة «طلبات بانتظار موافقتك» في تبويب الطلبات، دون الصلاحيات الإدارية الأخرى. الربط بمسؤول واحد لكل موظف. إلغاء الصلاحية أو الربط أو حذف المسؤول يوقف الموافقات من السيرفر حتى للجلسات المفتوحة.

الموافقات تشمل الإجازات وتغيير/تبديل الشيفت وتصحيح البصمة والأذونات الإلكترونية الموقعة. التوقيع مطلوب لقرار الإذن الإلكتروني، وسبب الرفض إلزامي، والقرار يسجل باسم الموظف المعتمد. لا يسمح بمراجعة طلب الموظف الشخصي أو تبديل يؤثر عليه، ولا بيانات شركة أخرى أو أقسام خارج النطاق. القائمة تعرض حتى 100 طلب من كل نوع، وتحديثها بعد المراجعة يعرض البقية. لا تمنح هذه الميزة تعديل الإعدادات أو إنشاء الحسابات أو الاطلاع على كلمات المرور.

## إعدادات إصدار iOS ومراجعة Xcode

المصدر المعتمد هو `mobile/app.config.ts` والإضافة `mobile/plugins/withNativeIosRelease.cjs`. مجلد `mobile/ios` يُولّد بواسطة Expo، ولا تُعدّل Pods أو ملفات المشروع الناتجة يدويًا. احتفظ بنسخة من أي تعديلات محلية مهمة خارج مجلد المشروع قبل إعادة التوليد النظيف.

- الحد الأدنى الحقيقي هو iOS 16.4، ويضبطه Deployment Target. يُحذف `LSMinimumSystemVersion` لأنه مفتاح macOS ولا يحدد دعم iOS.
- إصدار التطبيق 1.0.0 ورقم بناء iOS هو 3 في Info.plist وإعدادات Debug وRelease. قبل رفع إصدار جديد إلى Apple، ارفع `ios.buildNumber` في المصدر إذا كان الرقم السابق قد رُفع بالفعل.
- Expo ينشئ ملف Entitlements، والإضافة تضبط مساره النسبي في كل إعداد بناء. الفحص يفشل إذا فُقد الملف أو اختلفت Associated Domains. قيمة APNs المحلية development طبيعية؛ ملف التوقيع وحساب Apple يحددان صلاحيات التوزيع الفعلية.
- الموقع الدقيق يُطلب لتسجيل البصمة، مع إذن دائم اختياري لتذكير الوصول إلى العمل عبر Geofencing. لا توجد بصمة تلقائية في الخلفية. أُزيلت صلاحية الحركة وتُعطّل الشيفرة الخاصة بها. رسائل الموقع الدقيق والصور والتحقق المحلي عربية. تصريح الشبكة المحلية عربي في Debug ويُحذف من تطبيق Release النهائي مع Bonjour واستثناء الشبكة المحلية.
- User Script Sandboxing مضبوط على NO لخطوات بناء React Native. Swift يبقى في وضع 5 الذي تستخدمه الحزم الحالية. تحديثات Expo المتوافقة مع SDK 58 تقلل مشاكل المكتبات، ولا تعني اختفاء جميع تحذيرات APIs القديمة أو Swift 6 في Pods.
- OTA معطل عمدًا؛ توزيع التحديثات عبر المتاجر. لا تغيّر ذلك دون إعداد خدمة التحديث وسياسة runtime واختبارها.

Node 22.22.0 مناسب. استُخدم npm 11.9.0 لتجنب مشكلة تثبيت optional peers مع npm 10. من داخل `mobile` وبعد حفظ أي تعديلات محلية على مشروع iOS:

```bash
npx --yes npm@11.9.0 ci &&
./node_modules/.bin/expo prebuild --platform ios --clean &&
node scripts/verify-ios-config.cjs &&
open ios/*.xcworkspace
```

لتشغيل التطبيق على المحاكي دون شاشة خادم التطوير:

```bash
./node_modules/.bin/expo run:ios --configuration Release
```

الأرشفة والتثبيت على iPhone يحتاجان Team وملف توقيع مناسبين. النسخة غير الموقعة الناتجة من CI ليست ملف توزيع للموظفين أو App Store.

### الخصوصية وApp Store Connect

`mobile/config/privacy-manifest.json` يصرح بالبيانات المرسلة إلى السيرفر والمرتبطة بحساب الموظف لغرض وظائف التطبيق: الاسم، البريد، الهاتف، معرف المستخدم، الموقع الدقيق عند البصمة، الصورة عند اختيار رفعها، محتوى الطلبات والتوقيعات، ومعرف جهاز الإشعارات. لا يوجد تتبع إعلاني. إدراج نوع بيانات لا يعني طلبه من كل مستخدم؛ بعض الحقول اختيارية حسب الوظيفة وإعدادات الشركة. بصمة الوجه أو الإصبع ورمز فتح الهاتف تبقى لدى نظام التشغيل؛ التطبيق يتعامل مع تحقق Passkey ومفتاحه العام.

تُجمع أيضًا إعلانات Required Reason APIs الخاصة بالحزم عبر CocoaPods. راجع إعلان الخصوصية وسياسة الشركة وحقول App Privacy في App Store Connect وفق الاستعمال الفعلي قبل النشر؛ تحديث الملف هنا لا يملأ بيانات المتجر تلقائيًا. حدّث التصريح إذا أضفت حزمة أو نوع بيانات جديدًا.

### التحقق قبل الأرشفة

عدم وجود XCTest داخل Scheme لا يعني عدم وجود اختبارات؛ اختبارات منطق التطبيق تعمل بواسطة Node خارج Xcode. أُضيفت اختبارات تمنع فقدان Entitlements، واختلاف النسخ، والصلاحيات الزائدة، وإعلان جمع بيانات فارغ. CI يولد مشروع iOS ويفحصه ثم يفحص Info.plist وPrivacyInfo داخل حزم Release الناتجة للمحاكي والجهاز. هذه الفحوص لا تختبر اعتماد APNs أو Passkey أو دقة GPS على جهاز حقيقي؛ يلزم تجربتها باعتمادات الشركة.

```bash
npm test
node scripts/verify-ios-config.cjs
# على Mac بعد بناء Release، استخدم مسار .app الفعلي:
node scripts/verify-ios-config.cjs --bundle /path/to/wfrdwam.app
```

## تحسينات الآيفون وبصمة الدخول وتذكير الوصول

من «حسابي ← أمان البصمة والباس كي» يمكن تفعيل فتح الجلسة بـFace ID أو بصمة الجهاز. تُحفظ الجلسة باستخدام SecureStore مع requireAuthentication وبخدمة Keychain مستقلة، وتُحذف النسخة غير المحمية. عند نقل التطبيق للخلفية تُقفل الواجهة وتُمسح البيانات المؤقتة من الذاكرة. إلغاء طلب البصمة يبقي الحساب مقفلًا؛ كلمة المرور وسيلة استعادة إذا تغيرت بصمات الجهاز أو بطل المفتاح. فتح الجلسة بالبصمة لا يحل محل Passkey الذي تتحقق منه الشركة عند تسجيل الحضور.

من «حسابي ← الموقع وتذكير الوصول» يظهر إذن الموقع أثناء الاستخدام والخلفية، وزر إعدادات الهاتف. يُطلب إذن الخلفية فقط بعد تشغيل الموظف خيار تذكير الوصول والموافقة على شرح الاستخدام، مع إذن الإشعارات. يتم رصد دخول نطاق مواقع العمل المسموحة محليًا (بحد أقصى 20 موقعًا) وإظهار تذكير واحد لكل فترة أثناء أول ساعة من بدايتها إذا لم توجد بصمة دخول في آخر مزامنة. هذا التذكير لا يحتاج APNs/FCM أو تفعيل إرسال السيرفر. خدمة Push الأصلية لتذكيرات الحضور والانصراف ما زالت تحتاج إعداد الاعتمادات كما سبق.

التذكير ليس تسجيل حضور ولا إثباتًا للموقع؛ لا تُرسل أحداث Geofencing أو مسارات الحركة إلى السيرفر. يتوقف العمل بالخطة المخزنة بعد 24 ساعة كحد أقصى، وتجددها زيارة الرئيسية عند الاتصال بالسيرفر. إذا سجل الموظف حضوره من جهاز آخر ولم يحدث التطبيق، قد يظهر تذكير بسبب الحالة المخزنة؛ افتح التطبيق لتحديثها. يُحذف إعداد التذكير وخطته عند الخروج أو تغيير الحساب، ويُوقف عند سحب الإذن أو زوال المواقع المسموحة. استجابة النظام قد تتأخر وإغلاق التطبيق بالقوة يؤثر عليها؛ لا تُعتبر بديلًا مضمونًا لتذكيرات السيرفر.

يلزم نشر تحديث السيرفر الجديد لتوفير المواقع المسموحة فقط ضمن `/api/mobile/employee` ثم بناء نسخة التطبيق الجديدة. لا توجد هجرة لقاعدة البيانات. في iOS راجع وصف الاستخدام الدائم وخاصية location في Background Modes؛ وفي Google Play يلزم استكمال إفصاح استخدام الموقع في الخلفية ومراجعته قبل النشر. يُشرح للموظف الغرض قبل طلب الإذن، والخيار متوقف افتراضيًا.

خطأ kCLErrorDomain 0 قد ينتج عن عدم توفر GPS أو عدم ضبط موقع المحاكي. التطبيق يعيد محاولة الحصول على موقع حديث بدقة مناسبة بمهلة إجمالية 30 ثانية، ثم يعرض رسالة عربية. لا يستخدم موقعًا قديمًا أو وهميًا لتجاوز تحقق السيرفر. على Simulator اختر Features → Location وحدد موقعًا للتجربة، ثم اختبر GPS وFace ID والتذكير على آيفون حقيقي.

تحسينات العرض الحالية مكتوبة في React Native مباشرة: صف مستقل لكل مفتاح، أزرار بعرض متاح كامل، فصل الاسم المختلط عربي/إنجليزي، ومسافة آمنة أسفل المحتوى عند شريط التبويبات. لم تُستخدم مخرجات تصميم من Sleek قبل ربط الحساب وتوليد تصميم فعلي.
